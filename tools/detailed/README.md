# Detailed instruction output → SM viewer

The viewer accepts these forms of **simulation output**:

- Native FlashGPU-Sim `INSTRUCTION_ISSUE` runtime log records, as timestamped
  instruction observations. A pinned optional CPU-only build/run path and an
  actual validated vector-add capture are included below.
- `gpu-sim-instruction-observer-v1`, a custom JSON contract for a backend observer
  that actually records instruction intervals or points. Accel-Sim requires such
  an output observer; this contract is **not** an importer for its input SASS
  `.tracez` / `.traceg` files.

## SM instruction lights (default detailed sample)

The default SM view now uses the [native pipeline capture](../../examples/flashgpu-vectoradd-pipeline.json).
A small [observer patch](flashgpu-pipeline-observer.patch) records actual instruction
UIDs and `ISSUE`, `OPERAND_COLLECT`, `OPERAND_READY`, `EXECUTE`, `EXECUTE_END`,
`WRITEBACK`, `COMPLETE` hook cycles from the pinned FlashGPU-Sim source. It does
not alter pipeline scheduling/timing state. The patch is applied to a clean pinned
checkout, built, run with `GPU_SIM_PIPELINE_OBSERVER=1`, then removed from the tracked
sources. Original notices for the patch context are retained in
[FLASHGPU_COPYRIGHT.txt](FLASHGPU_COPYRIGHT.txt).

```bash
node tools/detailed/run-flashgpu.mjs --cuda /usr/local/cuda-12.8 \
  --output /tmp/flashgpu-vectoradd-pipeline --jobs 16 --pipeline
node tools/detailed/convert.mjs --input /tmp/flashgpu-vectoradd-pipeline.log \
  --output /tmp/imported-pipeline.json
```

The actual validated capture has 176 completed dynamic instructions, 1,136 native
points, 488 measured stage-transition intervals and 190 residence intervals, across
2 observed SMs / 8 warps. All 256 vector-add outputs pass the CPU check; the simulator
still reports the baseline's 6,212 cycles. [Native log](../../examples/flashgpu-vectoradd-pipeline.log)
and [manifest](../../examples/flashgpu-vectoradd-pipeline.manifest.json) retain patch/config/log/JSON
hashes, hook locations, actual unit/partition configuration and measured scope.

In the workbench, click **SM 内部** or **加载 SM 光点**. The component city is primary;
the instruction list is expandable. Select an observed SM and partition, or the
four-partition overview. Glowing moving lights identify instruction transitions;
lights inside components identify recorded residence intervals. Click a light to
inspect PC, warp, dynamic UID, and jump between that instruction's native stages.
Pause/seek/rewind calculate positions directly from simulated time. Untimed activity
is never extended into fabricated instruction intervals.

`normalizeFlashGpuPipelineLog(log, metadata?)` recognizes `FLASHGPU_PIPELINE_CONFIG`
and `FLASHGPU_PIPELINE` JSONL lines. It validates the actual sub-core configuration,
scheduler→partition map, native functional-unit identity, stable UID identity and
stage order. Only retained observations of the same UID/SM form interval endpoints.
Incomplete windows remain incomplete. Generic observer JSON from other backends
retains explicit component mappings without claiming this native hook contract.

The drawing follows a logical schematic. Native ISSUE insertion maps to Dispatch;
collector allocation/readiness map to Operand Collector; native execution-unit
identity selects the drawn FU. A shared native MEM unit is placed by the issuing
partition for inspection, without asserting separate physical LSU instances.
Load EXECUTE→WRITEBACK intervals include memory wait; they are lifecycle progression,
not measured wire or memory-transaction transit. Stores may COMPLETE at native LSU
retirement before global visibility. Missing writeback/cache/NoC stages remain
unknown. [Detailed validation](../../docs/sm-light-validation.md).

## Run the native instruction example

The bundled [vector-add trace](../../examples/flashgpu-vectoradd.json) and
[native log](../../examples/flashgpu-vectoradd.log) were generated by actually
building and executing unmodified FlashGPU-Sim at the pinned revision below,
using its H100 configuration. This is execution-driven PTX simulation on the
CPU. The independently authored [workload](vector-add.cu) adds 256 elements
with two CTAs of 128 threads and checks every result against the CPU answer.
The [capture manifest](../../examples/flashgpu-vectoradd.manifest.json) records
source/config/runtime/log hashes, toolchain, observed scope and measured wall time.
No physical GPU is required. The runner was verified with CUDA Toolkit 12.8,
GCC/G++, Make, Flex, Bison,
zlib development headers, Git and Node.js are needed for this optional runner.
The browser sample and playback require only the usual Node.js/static site setup.

```bash
node tools/detailed/run-flashgpu.mjs --cuda /usr/local/cuda-12.8 \
  --output /tmp/flashgpu-vectoradd --jobs 8
node scripts/validate-trace.mjs /tmp/flashgpu-vectoradd.json
```

The runner fetches the exact official commit into a cache, checks its identity
and clean tracked source, cleans cached objects, rebuilds with `TRACE=1 FLASH=1`,
links the workload
with shared `libcudart`, verifies which runtime is loaded, and saves unmodified
stdout/stderr. An existing clean checkout may be supplied with `--source PATH`.
It copies the official `SM90_H100` config and changes only tracing to enabled,
`INSTRUCTION_ISSUE`, all SMs (`-trace_sampling_core -1`), using one OpenMP thread.
Every capture performs a full rebuild so previously disabled tracing cannot be
reused accidentally. Build/clean/compile logs are saved beside the output.
It rejects a failed process, missing simulation statistics or failed functional
validation before writing normalized JSON. Building is a separate offline task;
the browser never launches a simulator or uploads input files.

For the original point-only example, choose **FlashGPU-Sim · ISSUE/STALL 日志**. The macro run is retained.
The native observation panel precedes the architecture illustration; the bounded
warp/stage lanes follow the replay cursor and retain the selected event. Search
includes PC, raw instruction text, stage, warp and scheduler. The category filter
uses raw ISSUE/STALL stage labels while `args.op` retains the operation class.
Clicking an instruction locates its actual cycle. Current-cycle or explicitly
labelled latest prior-cycle snapshots show points without inventing busy intervals.

Hand-written protocol tests remain explicitly `evidenceKind: illustration`.
The native example has separate tests against its original log and manifest.
Accel-Sim has not been built or run by this adapter.

## FlashGPU-Sim native logs

The adapter grammar was checked against official FlashGPU-Sim revision
[`291fbe172332eb481556632a79eb9cfc93cf46bf`](https://github.com/FlashGPU-Sim/FlashGPU-Sim/tree/291fbe172332eb481556632a79eb9cfc93cf46bf):
[runtime tracing](https://github.com/FlashGPU-Sim/FlashGPU-Sim/blob/291fbe172332eb481556632a79eb9cfc93cf46bf/docs/tracing.md),
[scheduler record format](https://github.com/FlashGPU-Sim/FlashGPU-Sim/blob/291fbe172332eb481556632a79eb9cfc93cf46bf/src/gpgpu-sim/shader_trace.h),
[cycle prefix](https://github.com/FlashGPU-Sim/FlashGPU-Sim/blob/291fbe172332eb481556632a79eb9cfc93cf46bf/src/trace.h),
and [emission sites](https://github.com/FlashGPU-Sim/FlashGPU-Sim/blob/291fbe172332eb481556632a79eb9cfc93cf46bf/src/gpgpu-sim/shader.cc).
This reference revision identifies the inspected **format**, not the version of
a user's captured simulator run.

In an already working FlashGPU-Sim installation, enable the component in the
workload's `gpgpusim.config` and capture the workload process output:

```text
-trace_enabled 1
-trace_components INSTRUCTION_ISSUE
-trace_sampling_core 0
```

```bash
./workload > simulation.log 2>&1
node tools/detailed/convert.mjs --input simulation.log --output detail.json \
  --run-id my-kernel-run --revision ACTUAL_SIMULATOR_COMMIT \
  --backend-version ACTUAL_SIMULATOR_VERSION
```

These options follow the official tracing documentation; compiling/running the
workload still follows the backend's own setup. `-trace_sampling_core -1` selects
all SMs but can produce much larger logs. The import retains the sampled scope;
missing SMs and missing observations are not zero activity.

Native `ISSUE`, `STALL_SCOREBOARD` and `STALL_READY_NO_ISSUE` records retain the
observed GPU total cycle, SM, scheduler, warp slot, dynamic warp ID, PC, operation
class, instruction text and scoreboard producer class. Each becomes a
zero-duration point with `args.granularity: instruction` and capability
`instruction_observations`. It is never expanded to a made-up execution interval
or combined with the next PC into a guessed completion time. Repeated PC records
remain separate observations, and a reused warp slot with another dynamic warp
ID remains distinct.

The backend documents incomplete multi-issue and stall-cause coverage. The
current importer also does not consume L2/NoC/TMA output; different subsystem
clocks are not merged. CTA identity, active mask, instruction completion,
functional output correctness and memory routes are unknown from these records.
The logged `op` is an operation **class**; raw instruction text is retained
instead of claiming to extract an exact opcode. Producer classes do not become
dependency edges. The native `STALL_SCOREBOARD` label is a compound backend
readiness outcome and can also cover barrier/shared-memory/MIO conditions; it
must not automatically be translated into a proven RAW dependency.

## Custom interval observer contract

The following is a **protocol illustration**, not simulator output:

```json
{
  "format": "gpu-sim-instruction-observer-v1",
  "meta": {
    "title": "Illustrative observer contract",
    "producer": "Hand-written illustration; not a backend run",
    "producerRevision": "unknown",
    "backendVersion": "fixture-format-v1",
    "runId": "illustration-only",
    "timeDomain": "illustration.core_cycle",
    "timeUnit": "cycle",
    "evidenceKind": "illustration"
  },
  "instructions": [
    {
      "id": "observed-interval-0",
      "instructionId": "dynamic-instruction-0",
      "smId": 0,
      "warpId": 2,
      "pc": "0x100",
      "opcode": "IADD3",
      "start": 10,
      "end": 14,
      "stage": "observer-defined-issue-to-completion"
    }
  ]
}
```

`start`, `end`, `stage`, PC and instruction identity must come from the observer.
The adapter checks required identities and timestamps but cannot authenticate
the origin of an imported file. Use `simulation` only for actual backend output.
The observer must describe the meaning of each stage and its capture scope in
`meta.description`; a named interval does not imply complete pipeline coverage.
For points set `start === end`. Capability `instruction_spans` is emitted only
for nonzero intervals; mixed inputs declare both capabilities.

Optional `threadBlockId`, `dynamicWarpId`, `activeMask` and other observed fields
are retained. Hex addresses and masks are strings, preserving values beyond
JavaScript's safe integer range. `dependencies` defaults to no known edges and
may be provided only when actual completion dependency IDs are known. An
`instructionId` associates multiple observed records with one dynamic
instruction; it is not inferred from PC. The adapter also accepts canonical
trace v1 with matching validated instruction capabilities.

## Time and provenance

GTSim and detailed outputs are separate runs and retain independent cycle axes.
Matching numeric SM/CTA/warp IDs does not establish a cross-run mapping. Entering
an SM does not translate GTSim nodes into detailed instructions or substitute
simulator state while execution is in progress.

`runId`, `backendVersion` and `producerRevision` remain `unknown` when the input
does not provide them. `timeDomain` for native scheduler logs is explicitly
`flashgpu.gpu_total_cycle`; observer JSON must describe its own clock or use
`unknown`. The CLI records the input SHA-256. Without `--run-id`, it assigns
`import-sha256:HASH`, identifying the imported artifact rather than claiming the
simulator emitted that run identity.

Optional measured wall time can be supplied with both `--wall-time-seconds` and
`--timing-scope`. It is stored as `metrics.wallTimeSeconds` and
`metrics.timingScope`. Absent measurements stay unknown; no backend speed is
derived from simulated cycles, replay speed or the number of imported records.
The scope should state whether tracing, setup and output writing are included.

The library API is `normalizeFlashGpuLog(text, metadata?)`,
`normalizeDetailedTrace(json)`, `isDetailedTrace(json)` and
`detailCapabilities(trace)` in [lib/detailed-trace.js](../../lib/detailed-trace.js).
Detection validates both capability declarations and actual record shape;
a backend name or a tile operation named `wgmma` does not pass. Cache the
capability result when loading a run rather than validating the whole trace on
every animation frame. Input limits are 64 MiB / 500,000 log lines, 250,000
observations/intervals, and the canonical trace's 2,000-component limit.
