# 从执行可视化到可操作实验：五个探索方向

日期：2026-10-23。状态：针对 Daisen、Milestone 与现代异步 GPU 调试的研究构想；不是已实现功能、复现实验或新颖性证明。补充 [游戏与交互调研](games.md)、[TOG 评估](tog-publication-assessment.md) 和 [异步 GPU/DSA 关系调试](async-accelerator-debugging.md)。

## 1. 相关工作给出的出发点

Daisen 已经支持模拟器执行、组件、任务层级与依赖的交互探索，并用于寻找优化机会和检查改进；不能把它概括成被动播放器。Milestone 进一步采集阻塞解除事件与等待原因，保持跨层分析的上下文。它的讨论还区分“证据根本没采集”和“用户不懂已有证据”的问题。[Daisen 作者页面](https://vis.khoury.northeastern.edu/pubs/Sun2021DaisenFrameworkVisualizing/)、[Milestone 作者原文](https://sarchlab.org/vis_the_invisible.pdf)

可继续研究的任务是：用户已经看到等待或错误之后，如何选择下一次观测、制造一个反例、比较两次执行，或者检验解释能否迁移到另一个配置。以下提出的是交互与分析方法候选；组合已有技术不会自动形成论文贡献。

## 2. 五种具体交互

### A. 平行执行：一个修改的影响从哪里开始

**用户动作。** 复制一次实验，只改一个明确参数，重跑后选中相同的逻辑输出。系统在两次执行中联动对应的工作，突出依赖、资源等待和完成次序的差异。用户再做第三次针对性修改，检验自己对差异的解释。

**示例。** 先用仓库已有 GTSim 基线和低 L2 带宽样例，追踪同一个任务为何更晚完成。后续接入真实流水线后，再调查“两级改三级缓冲为何可能改善隐藏延迟，也可能因资源占用增加而降低并发”。后者是待构造实验，当前独立时钟模型不能直接证明这条完整机制。

**研究问题。** 当 tile、fusion 或调度改变，一项工作可能拆成多项或合并，怎样保持逻辑工作/数据版本的跨运行对应，并提取帮助验证解释的差异切片？第一处观测差异不自动是根因；按时间戳、相同 event ID 或画面位置配对都不充分。第一版可以仅支持固定 workload 与明确的一对一映射，无法对应时显示未知。

**验收。** 独立核对配对正确性，测定位准确率、验证解释所需重跑次数和时间；比较完整 trace 的人工 A/B、已有统计差分与新方法。候选贡献是对应和诊断方法，双屏动画只是界面。

### B. 调度实验室：亲手构造一条失败路径

**用户动作。** 暂停在存在选择的状态，决定哪个已具备执行条件的操作先推进；例如让下一轮 producer 更早到达复用位置，观察前一轮 consumer 是否仍在使用该区域。构造失败后，系统提取相关事件，用户修复同步，再让搜索器尝试反驳修复。

**乐趣。** 从“看着别人解释 race”变成“我亲手证明这段程序会出错”。用户也可自定目标，例如在保持正确的前提下探索尾部延迟，不必先完成固定关卡。

**研究问题。** 能否把大量等价的合法交错压缩成少数对开发者有意义的选择，并把反例映射到 tile 版本、异步操作和 barrier 代次？可比较随机扰动、自动搜索、人引导搜索的反例发现成本，以及用户在未见 kernel 上的修复能力。没有找到失败只表示搜索范围内未发现，不能显示为全域正确。

**实现边界。** 需要新增可重放决策接口、允许推进的状态和正确性判定。模型必须明确指令次序、完成/可见性规则、公平性与延迟范围，不能靠无限冻结某个执行者制造无意义失败。当前符号 SM 模型不执行任意 PTX 数值，TMA/tcgen05 的真实竞态需要新语义后端与实机核验；在界面上拖动事件不会控制实机硬件调度。

### C. 有限观测的侦探：下一次该记录什么

**用户动作。** 面对一个晚完成的 tile，当前证据同时兼容“搬运服务慢”“发射前等 buffer”“同步代次有问题”等解释。用户选择下一次记录哪类事件，系统说明每个探针可以区分什么，再重跑更新证据。探针按实际可提供的信号定义，不能假设每个硬件完成时刻都可直接读取。

**乐趣。** 每次观察都有目的，也可能推翻自己的判断。自由模式不强加积分，用户可以展开所有模型证据；挑战模式才设置记录预算。

**研究问题。** 在记录成本与重跑次数有限时，怎样选择最能区分候选解释的观测，且正确保留尚不能判断的关系？如果提出自动推荐，可先针对明确的有限候选模型，不必假装已有所有 bug 的完备知识库。

**验收分两步。** 第一阶段用完整模拟轨迹作为隐藏真值，控制遮蔽字段，比较固定、随机、专家与系统建议的探针选择，测诊断正确率、证据预算及错误确信。它只能验证交互或选择策略。第二阶段实现真正的选择性 collector，测运行开销、日志量、重跑成本和插桩扰动，才能主张节省采集。多次重跑的证据保留 run 身份，不能拼成一次执行的完整因果时间线。

### D. 优化适用范围地图：在哪里快，在哪里失效

**用户动作。** 将一个优化方案放到 shape、stage 数、tile 配置等二维空间，点击相邻配置，观察吞吐变化或失败，并请求解释边界两侧的机制差异。用户也可带着自己的预测寻找一个反例。

**示例。** 某配置在一组整齐 shape 上表现好，尾块、迭代次数或资源阈值改变后，出现不同执行路径或优势消失。界面把“数值检查通过”“发现反例”“模型范围内已验证”“尚未测试”分开编码；颜色不能把离散测试点之间的区域自动认证为安全。

**研究问题。** 参数扫描和 autotuning 已是常规方法。候选增量是用跨运行语义差异解释适用范围的边界，并选择少量有辨别力的边界实验。比较扫描效率、边界发现率、解释预测后续配置的准确性；不能只报告又找到一个更快参数。

**实现边界。** 教学模型可先画模型周期和资源约束地图。真实正确性地图需要数值执行/reference 与覆盖多配置的检查；性能需要实测或明确验证过的模型。阶段数、shape 的改变可能触发重新编译，必须保留编译与执行身份。

### E. 跨加速器搭建：把同一个流水线搬到另一台机器

**用户动作。** 给同一个小计算任务两套执行/存储规则，组合搬运、局部存储、计算和消费，找出哪些设计可复用，哪些等待或复用规则需要改变。一个已搭通的模块可以继续组合使用。

**研究问题。** 数据版本、资源所有权与完成令牌能否形成共享表示，同时显式表达各后端不可替换的规则？可以研究跨硬件诊断与设计迁移；不能仅统一术语或更换芯片外观。

**实现边界。** 首先是一个真实 GPU 后端，再考虑 TPU/Pallas 的代表任务。Pallas 的 HBM/VMEM 搬运与 semaphore 是具体第二实例，远程 DMA 还有不同的发送/接收完成条件；TPU SMEM 也不等于 NVIDIA shared memory。[Pallas 流水线](https://docs.jax.dev/en/latest/pallas/tpu/pipelining.html)、[分布式 DMA](https://docs.jax.dev/en/latest/pallas/tpu/distributed.html)。目前没有 TPU 后端，只能将新增抽象机器标为玩具模型。

## 3. 建议先做什么

优先把 **A（两次执行找分叉）＋C（选择下一次观测）** 做成一个完整循环：看到差异 → 提出多个解释 → 补证据或改一个因素 → 重跑 → 检验解释。它利用现有模型、事件来源与外部 trace，且不会要求先完成精确 Blackwell 微架构仿真。

最小原型从同一模型、同一 workload、固定逻辑身份开始。选一个模型确实支持的带宽/依赖问题，新增配对视图、证据能力声明和少量可区分的观测。当前仅有独立回放，尚无并排 A/B 或上述自动配对；无界队列模型也不能承担有限 buffer 背压的实验。

B 最适合接续上一轮 TMA/tcgen05 方向做鲜明演示；D 可在真实 kernel 后端建立后成为实用分析工具；E 是较长期的 DSA 扩展。自由创建实验、保存与分享是产品底座，本仓库既有设计已提出这些能力，不将其重新包装成方法贡献。

若研究重点是差异表示、观测选择和诊断工作流，VIS/TVCG 值得优先考虑；若核心是调度空间压缩、验证或生成，则看系统/编译/验证社区；若主要证据是学习迁移，则评估 HCI/计算教育。要继续面向 TOG，应挑选有实际社区价值的图形、图像处理或可微渲染任务，并建立相应的方法贡献与结果；加入城市或游戏外观本身不能判断录用潜力。

这是有针对性的近邻检索与研究设计，不是穷尽式综述。后续选择其中一条时仍需精读对应社区的差分执行、主动诊断、并发探索或调度综合工作，再收敛新颖性主张。
