## 3. 两条件比较的对象及公平性

两组初始可见内容都是相同的任务合同、文件目录、case 元数据和已知限制；不一次发送整个源码文件。两组同样拥有 `list/search/read/case`。`search` 是跨给定文件的字面搜索，`read` 每次最多 120 源码行，所有实际观测通过相同 API 获取。

诊断组额外可选 `contrast`、`observed`、`source_links`，以及在受支持 TMEM 捕获上才有效的 `overlap`。本轮新病例不包含 TMEM allocation 捕获；不能把一次 unsupported `overlap` 请求误计为有效重叠诊断。通用操作只汇集实际状态／观测、按给定参数分组、沿显式 source/provenance 关联，不读取 gold 位置或附加缺陷专用修复规则。

两条件共享最多 8 次请求、9 次模型调用、每响应 16,000 个和累计 64,000 个 JavaScript UTF-16 字符、每调用 90 秒／每 trial 600 秒。错误和超限请求计入预算；超大响应明确拒绝，不静默丢弃尾部。相同预算上限允许不同实际消耗，后者正是需要测量的结果。

初次请求不强制使用普通或专用工具，也允许直接提交答案。因此该比较回答的是：**在相同原始事实和访问预算下，开放这些派生证据操作是否改变本组任务的行为及正确修复结果**。它不是“有工具对完全没有源代码”，也不是文字 agent 对视觉界面的用户研究。

调用采用空临时 cwd、ephemeral 会话、忽略用户配置、禁 shell、结构化回答和 JSONL 外部调用审计。它支持有限 API 暴露和可追查执行；不是形式化安全沙箱，也不是训练记忆排除机制。模型别名为 `gpt-6-astra`，CLI 为 `0.161.0`；未获得权重快照 ID，不能把别名写成已固定的精确权重版本。

## 4. 调度与重复的统计解释

每个根因／重复序号形成一个时间块，两条件并发执行，最多两个 trial 同时活动。第一、三次重复按原顺序运行，第二次反转根因和条件顺序。它有助于减少整体时段变化对条件的影响，但**不是随机化分派**；三个重复也没有提供共同随机 seed。所谓配对是同一个根因和重复时间块，不意味着两次生成共享潜在随机轨迹。

设 `Y[i,c,r]` 为原始模型补丁达到冻结主终点的 0／1 值。对每个根因 `i`，先报告 `R[i,c] = sum_r Y[i,c,r] / 3`；再给出六个根因的差值 `Δ[i] = R[i,diagnostic] - R[i,raw]`，以及等权平均 `mean_i Δ[i]`。在本轮均衡设计下，该平均与两组各 18 次尝试的成功比例差数值相同，但有效独立根因仍只有六个。

主表应展示六个逐根因结果，并补充整体成功数。不要把 36 次调用、64 个隐藏输入或数百万输出元素当作独立开发者／缺陷样本来计算显著性。当前根因数、便利选择和非随机调度不足以支持总体“普遍提速”的强推断；优先报告完整结果向量、效应大小、失败原因和不确定边界。任何事后置信区间、检验或新的指标应明确标为探索性分析，不能追称为原冻结主分析。

## 5. 主终点：隐藏成功与完整回归要分开

冻结主终点依次要求：模型调用合法、精确补丁可原样应用、候选实际编译／JIT 执行成功、所有预定义隐藏 case 通过，且候选树、隐藏合同和独立验证 receipt 身份对应。失败调用、解析错误、无补丁、无法应用、编译失败、超时、缺失产物与隐藏失败均留在 36 项计划分母中。它们是不同失败类别，不应合并成编译器自身的数值错误。

两个 evaluator 都实际运行可见和隐藏合同，并保存 `visibleCases`。但是冻结 `scoreRuntime` 的成功判断只要求精确的隐藏 case 集合；**它不会自动将可见回归失败加入主终点**。因此必须分别报告：

1. 冻结主要指标：所有隐藏用例通过；
2. 补充回归指标：所有隐藏及可见用例同时通过；
3. 可见通过对照的回归数与失败类型。

第二项是合理的补充解释，不能事后替换主终点而隐去原始结果。若出现“hidden 通过但 visible 失败”，必须明确标出，不能写成“完整修复通过”。同样，JIT 可执行不代表语义正确、性能最优、无数据竞争或全部库测试通过。

原样多文件编辑是必要条件：不得只摘取候选在官方目标文件中的修改、补齐语法、恢复被它破坏的其他源码或用官方 patch 替换候选。完全相同候选若共享一次实际验证，可以同时归于两个模型尝试，但必须按完整候选树及执行合同哈希绑定，并分开统计模型尝试数、唯一候选数、物理 GPU 运行数和摊销成本。

## 6. 定位引用评分的能力与局限

冻结评分器允许引用所有给定源，包括 generated IR／可见 kernel；每个区间不超过 40 行；至少一个有效区间需命中事先声明的相关函数区域。引用必须绑定同一 case 的合法 evidence，并覆盖实际失败及要求的通过观测。共享静态 IR 不能同时充当失败和通过观测；这一点有独立对抗测试。

`supportedLocalization` 仍是**区域命中加观测引用合法性**，不是解释全文的语义或因果正确率，原因包括：

- 区域通常是相关函数，命中函数不等于准确指出错误语句或机制；
- 每个区间长度受限，但位置条目总数没有冻结上限，也没有对多余有效区间施加精度惩罚；
- 引用 ID 必须真实且属于该 case，但评分器不要求 agent 此前确实通过 query 获取过该内容；
- 合法的事实引用可以支持错误的推理链，当前机器评分不逐句判定解释。

保留原分数，并在结果分析中描述位置条目数、累计引用行数、实际 source/search 获取范围和观测 ID 获取覆盖，可帮助判断分数是否来自宽泛引用。后加日志指标只能作为补充；不能改变原始分母或回写冻结分数。若要声称“解释让人理解”，还需要独立于该命中评分的理解任务与评价。

## 7. 可选工具使用与 intent-to-treat

诊断组的主要比较应按**分配条件分析（intent-to-treat）**：所有被分配到 diagnostic 的 18 次尝试均保留，包括未使用专用工具、只作普通读取、工具报错、超限、误用或最终失败的尝试。不能只选择实际调用成功的用户子集与全部 raw 比较。

另报告每种专用操作的实际请求数、获得非错误返回的次数、响应字符量、发生轮次及使用 trial 占比。将“请求 uptake”和“有效返回 uptake”分开，明确 unsupported 操作不会自动产生诊断收益。

工具使用者与未使用者之间的成功率差是选择后的相关性：更困难的任务可能更需要工具，更熟悉问题的 agent 可能直接完成，因而不构成工具效果的因果估计。不能据此说“用了工具就提升了某百分比”。

## 8. 成本口径和失败时间

冻结实现记录了下列不同量，不应混为一个速度指标：

| 量 | 正确解释 | 不能直接解释为 |
|---|---|---|
| 请求数、响应字符 | 实际 API 获取／派生证据量 | 独立事实数量、源码理解量 |
| `modelWallSeconds` | 所有调用的服务、网络、排队及生成墙钟总和，包含失败调用 | 纯推理耗时、开发者工作时间 |
| trial `wallSeconds` | runner 所记录的生成、查询和候选写入范围 | 包含构建和 GPU 的端到端修复时间 |
| query 墙钟 | 本地纯查询与序列化附近的处理时间 | GPU 算子耗时 |
| evaluator `wall_seconds` | 其计时起点之后的子进程/JIT/执行及验证范围 | 包含前置源复制／overlay和调度等待的完整耗时 |
| CLI usage | 实际返回的 input/output/cache/reasoning 字段 | 可任意相加的独立 token 或准确账单 |

失败或 timeout 调用可能没有 `turn.completed` usage。应列出“有 usage 的调用／全部调用”，把缺失记为未知；已记录 token 总量是可观测部分，不能把缺失当零成本。缓存、reasoning 和 output 字段可能有包含关系，不能直接累加为计费量。重放历史产生的输入 token 也是实际成本，应保留。

生成成功和失败的全部尝试都应进入时间／查询成本描述。仅对成功子集求中位数会产生选择偏差，可以展示，但必须同时展示成功数、失败耗时和 timeout 数；快速生成错误补丁不能被称为效率高。没有完整串联的时间边界时，`modelWallSeconds + evaluator.wall_seconds` 只能标为记录范围内的阶段时间总和。

## 9. 零反馈实验能支持什么

本轮不是交互式编译—修复循环。多轮模型调用用于读取证据，最终只提交一份候选；没有编译反馈、隐藏结果回馈或根据验证结果第二次修改补丁。它测量的是同等访问预算下的最终诊断／补丁质量和证据获取成本。

协议要求全部 36 个生成结果固定后才运行模型候选的 GPU 验证；官方 before/gold 的预先校验不违反这一顺序。**该顺序在本审查时是待核验的执行条件**，因为候选采集尚未结束。结果收尾时应比较所有计划尝试的生成结束时间与最早候选 evaluator 开始时间，并保留无反馈记录。不能仅凭工具目录存在或承诺就写成已经验证。

此设计可支持有限结论：“在这六个公开、有限源码范围的真实 GPU 缺陷上，开放指定证据操作后，模型最终修复结果／获取成本发生了怎样的观察变化。”不能单独支持“迭代调试快多少”“首次修复速度普遍提升”“人类更理解 GPU”“可视布局更有效”或 Blackwell 异步流水线／tcgen05/TMA 的一般诊断覆盖。

## 10. 结果发布前的固定核对项

1. 36 个调度项全部有原始结果；缺失、失效和 timeout 原样列出，不重抽有利样本。
2. 全部完成后，重放提示词、最终模型消息、查询预算、原始补丁和冻结定位分数。
3. 绑定实际候选树、native/source、隐藏合同、完整输出与独立 verifier receipt；分别统计唯一候选和物理执行。
4. 核验全部候选先生成、后执行，期间没有候选结果反馈给模型。
5. 主表保留六个根因的 raw／diagnostic 三次结果、隐藏主终点、可见回归、工具 uptake 及失败成本。
6. 结论以实际正、负、零结果为准。若基线仍出现天花板、工具不使用或成本更高，应直接报告，不据此回改工具、病例和评分。

本审查不读取当前成绩，也不预断工具会获益。冻结与审计让结果可解释；论文结论的强度仍由真实执行结果、任务覆盖和相应的人类／系统证据决定。
